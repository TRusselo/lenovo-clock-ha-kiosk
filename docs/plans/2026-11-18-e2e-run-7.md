## Findings, most important first

1. **The fastboot wait for the Magisk flash stops after 5 minutes.** At the Root step, the tool asked for fastboot
   mode at 18:44:12; the person was away, and at 18:49:12 it stopped: "Flashing stopped (no fastboot device after
   300 s). The clock still starts its old slot. Unplug its power and run the same command again." The rerun hit it
   again (18:54:43 to 18:59:44); the third found fastboot after 4 min 16 s, under the limit by luck.
   - **Cause:** `fbmulti()` (`lck/flash.py`) starts `fbmulti.py` before asking for fastboot, and the downloaded
     `fbmulti.py` exits on its own after 300 s with no device (its line 6). The wait loop ends when the process
     exits, and the error is raised as a stop.
   - **Every other mode wait keeps going**, and the guide says so ("It keeps waiting as long as you need"). Someone
     walking off during a 75-minute setup is the normal case.
   - **Fix:** wait for fastboot mode first (as `wait_for_mode` does, with Clock mode shown), and only then start
     `fbmulti.py`; or start it again when it exits with "no fastboot device". This affects the slot A flash too,
     not just Root.
2. **A false ✓ before the stop.** The screen showed "✓ Flashing the patched boot image (0s)" right above the stop.
   When `fbmulti.py` has already exited, the `busy()` block after the wait ends at once and draws a ✓. Show the
   job only once fastboot was found, or end it with ✗.
3. **The USB pull reason is wrong.** The log says "BROM attempt 1 of 5 failed: the clock didn't reach BROM mode",
   but mtkclient had already been reading partitions. In `run_in_brom` (`lck/mtk.py`), a `MtkFailed` from
   `_follow` sets `text = ""`, so `why_failed` gets nothing and gives the empty-text reason. Read the output file
   after a failure instead, so "USBError"/"Errno 19" are seen: "the USB connection dropped. Nothing was written."
4. **Cast still covers Magisk.** The force-stop before opening Magisk gave enough time to do the Superuser steps,
   but "Link Account" came back over Magisk while the person was still at it. While the tool waits on the person
   in Magisk, it should check the front app every few seconds and, if Cast has taken it, force-stop Cast and bring
   Magisk back.
5. **Restore's second BROM session says "still held by the last try".** Restore reads the partition table in one
   session, then writes in another. The first leaves the clock at `0e8d:2001`, so the new stale check fires with
   "The clock is still held by the last try", which sounds like a failure. It's the normal flow: say "Now unplug
   the clock's power: BROM mode again, this time to write."
6. **After the backup, the fastboot box shows twice.** The clock is still in BROM after the backup. The tool drew
   the fastboot box, then at once "The clock is in BROM, working mode, not fastboot. Unplug its power and try
   again:", and the same box again (all at 18:38:23). Ask for the unplug first, as the stale check does.
7. **Root redoes the Magisk patch on every rerun**: about 1½ minutes each, three times here, though
   `boot-magisk.img` from the first try was on disk. Reuse it when it exists and was made from the same
   `boot-stock.img`.
8. **"The user data holds your Wi-Fi password from the backup"** (`lck/images.py:205`) was said after a typed
   network was added. Say "the Wi-Fi password you typed" when `wifi_new` is set, as the flash step now does.
9. **A short Wi-Fi password asks the name again.** After "A WPA2 Wi-Fi password is 8 to 63 characters", the tool
   asked for the network name again, not just the password.
10. **Log masking catches prose.** "Easier in a browser, for typing your Home Assistant address and token:" was
    logged as "token: ***   http://…": the secret filter treats the word "token:" in a message as a key. Harmless;
    worth narrowing the pattern so messages read right.
11. **"Found it. Let go of VOLUME UP" is logged twice**, before and after the "start normally" box (19:28:04):
    the line carried over to the redrawn box is logged again.
12. **"Nothing yet. If the screen lit up …" came too soon** during restore: logged 5 s after "Found BROM", and
    "Connected" followed 0.25 s later. The hint fired while the connection was in progress.
13. **The Wi-Fi name is logged** (`ANSWER <wifi-name>`). It's in the backup too, so probably fine; noted because
    logs get pasted into issues.

### Review findings, most important first

1. **Leaving fastboot after the flash starts still waits 300 s.** `fbmulti()` (`lck/flash.py`) now starts
   `fbmulti.py` only once the clock is in fastboot, but nothing checks the mode while it runs. If the clock drops out
   right after (unplugged, a loose cable), the screen shows "Flashing… 0 of N" with no Clock mode line until
   `fbmulti.py` gives up after 300 s; only then is fastboot asked for again. **Fix:** in the busy loop, if the mode
   isn't fastboot and nothing is flashed yet, kill `fbmulti.py` and wait again at once.
2. **The Wi-Fi name is still logged.** The answer is logged as "(answer not logged)", but `lck/images.py:196` says
   "Added the Wi-Fi network <name> to the clock's user data.", which goes into the log (run 7 has it at 18:39:12).
   Leave the name out of that message, or say it with `log=False`.
3. **Log masking misses `key: value` with a space.** The new pattern (`lck/log.py:17`) masks `key=value` and
   `key:value`, but not `password: hunter2` or `token: abc`, which the old one did. Keep masking those, and leave
   out only what is plainly prose, such as a value starting with `http`, or the end of a line.
4. **The "started normally" hint is gone for the case it's for.** In `_follow` (`lck/mtk.py`), once BROM is seen
   the hint never fires again in that try. Someone who lets go of VOLUME UP as BROM shows, before mtkclient catches
   it, gets a clock that starts Android, and USB shows nothing from then on: that's the hint's case. Use a time
   since BROM instead, as `wait_for_mode` does with `STARTED_AFTER`.
5. **Cast isn't watched at Magisk's first OK.** `keep_magisk_in_front` wraps only the Superuser prompt. In
   `_first_run` (`lck/root.py`), "Link Account" can cover "Requires Additional Setup" before it's tapped; the wait
   then times out after 180 s and asks whether to carry on with Magisk's setup not done. Wrap that wait too.
6. **"Unplug first" can interrupt a fastboot retry.** `wait_for_mode` (`lck/modes.py`) now asks for an unplug
   whenever a fastboot wait starts with the clock in BROM. On `fbmulti()`'s second try the person may already be
   holding VOLUME UP, passing through BROM on the way to fastboot (the box says that's normal), and gets told to
   unplug. Ask only after a BROM job (a flag from the caller).
7. **The patch stamp uses a typed-in Magisk version.** `MAGISK_VERSION = "31.1"` (`lck/root.py`) isn't tied to the
   pinned download, though its comment says it is. If the pin moves and this doesn't, a rerun reuses a boot image
   patched by the old Magisk. Stamp with the sha256 of the Magisk APK actually used.
8. **The Cast watcher can outlive its prompt.** The thread runs adb through `ctx.runner`; `join` gives up after
   34 s, and a hung adb call (Wi-Fi blip) leaves it running alongside the main thread's adb calls, possibly stopping
   Cast or relaunching Magisk after the prompt ended. Give its calls a short timeout and check `stop` before acting.
9. **The name is checked with a fake password.** `ask_wifi` calls `check_wifi(ssid, "x" * 8)`, tying the name
   check to the password rules. Split `check_wifi` into a name check and a password check.
10. **Restore shows two "BROM again, to write" boxes.** The new `NEXT_SESSION` box ("…BROM mode once more, this
    time to write… then do the steps below") is followed by `BROM_AGAIN` ("BROM mode again, this time to write.
    For BROM mode: unplug…"): two boxes in a row asking for the same unplug. Use `BROM_PROMPT` after it.
