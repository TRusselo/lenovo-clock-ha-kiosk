# E2E run 6: planned faults (dirty run)

**Goal:** stage the failures a real person runs into, and record for each one whether the tool soft-fails and
retries inside the run, or quits with "Stopped:" and log lines. The aim is that errors retry rather than quit.
Observed and logged here; the fixes go to the clock project.

**Code under test:** `android-things` at 0c458fb (Wi-Fi asked in step 1, typed Wi-Fi, `wifi` re-entry at the
address question with a userdata-only flash).

**Status: done.** A clock with no saved Wi-Fi went from stock to a working kiosk, through a wrong Wi-Fi password,
a USB pull, an accidental Ctrl-C, a stale BROM session and a power cut. All 15 steps done; three runs of the
command (the Ctrl-C, and the hard stop at the install). Backup 13:12 to 13:50; setup finished about 15:15.
Only the zip was kept at the end (`clock6.zip`, the folder removed): **run 5's fix 10 is now confirmed.**

## What retried, and what stopped

**Retried inside the run (the goal):**
- **The wrong Wi-Fi password** (the new loop): the clock came up with "Can't connect to Wi-Fi", `wifi` at the
  address question rebuilt the user data and flashed only that, twice, and the clock joined. No stop.
- **A wrong but valid address:** tried 3 times in 4 s, then asked again.
- **USB pulled during the BROM backup:** "That didn't take. Let's try again", and the next attempt read.
- **VOLUME UP alone for BROM:** works every time (not a fault, but the box can be simpler).

**Stopped the run:**
1. **Clock power cut during an adb step** (the install's copy): a 15-second timeout ended setup, with a raw
   Python command list as the message. The clock was back within a minute. Resume worked, but this is the main
   soft-fail to build: lost the clock, wait for it, redo the step.
2. **Ctrl-C, pressed to copy text:** stopped as designed, but a copy shortcut shouldn't throw away a
   35-minute backup.

**Would have stopped:**
3. **A rerun while the clock was still held by the last mtkclient session:** mtkclient attached to the leftover
   download agent, read 0 bytes, and failed. The tool retried 3 times, never saying to unplug the power (the only
   way out). Attempt 4 of 5 worked only because the user power-cycled when asked here.

**Needed a hand to carry on:**
4. **Magisk covered by Cast's setup screen** within seconds, on a clock unlinked from Google. Stopping Cast
   (`am force-stop`) before opening Magisk fixed it.

## Findings, most important first

1. **Soft-fail adb steps.** A timeout or "device offline" in any adb step should mean "lost the clock": say so in
   plain words, wait for it (boot id, `sys.boot_completed`, and the address question if it's gone long), then
   redo the step. Never show the Python command list. (Fault 11.)
2. **Stale BROM session.** At the start of a BROM session, `0e8d:2001` means "the clock is still held from
   before": say "unplug the clock's power, then …", and wait until it leaves USB before starting mtkclient. Also
   treat "flash size 0x0" / 0-byte dumps as a failed attempt with that same advice. Seen twice today.
3. **Cast covers Magisk on an unlinked clock.** `am force-stop com.google.android.apps.mediashell` just before
   opening Magisk; while waiting for Enter, bring Magisk back if something covers it. Confirmed by hand.
4. **Set landscape system-wide** (test 12): `settings put system accelerometer_rotation 0` and
   `settings put system user_rotation 1` right after the connect step (adb, no root). Magisk came up landscape
   and the right way up for the first time. Then drop "it may be sideways", and check whether Kiosk Satellite's
   forced landscape is still needed (not checked this run).
5. **Ctrl-C during BROM:** ask before stopping ("Press Ctrl-C again to stop the backup"), and/or say in the guide
   to copy with Ctrl+Shift+C.
6. **Typed answers can't be backspaced past a wrap** (seen twice): `ui.ask` reads a plain line in cooked mode
   (lck/ui.py:414). Use `readline`, or ask on its own line with a short `> ` prompt.
7. **Two spinners at once** in the degoogle step flash many lines at about 30 a second: the outer busy line
   ("Switching off Google's apps") keeps redrawing while the inner one ("Waiting for Android to save the
   changes") runs. Pause the outer one, or make the inner wait a note on it.
8. **BROM screen:** clear old "Clock mode" lines on a retry (three were on screen); say why a retry happened
   ("the USB connection dropped; nothing was written"); and show "Waiting for BROM…" while the clock powers up,
   since the mode line only changes once BROM appears.
9. **The address box:** name the clock's own signs. The setup screen shows "Build=…, IP=…, Channel=…" at the top
   (the address, without swiping), and "Can't connect to Wi-Fi" when typed details are wrong. And "It reconnects
   to the Wi-Fi saved in the backup" is wrong when the Wi-Fi was typed.
10. **The log has no answers or messages**: only commands and exit codes. Record each question, the answer
    (never a password) and the tool's reply, and each BROM attempt with its number and reason.
11. **Small:** **YES** and **NO** in bold in the Wi-Fi question; the backup note says it holds "its Wi-Fi
    password" when there's none; the progress bar is drawn inside a cut-off "..." ("about 35 minut..  █░░.").
12. **Docs:** never factory reset to go back; use `lck restore`. A reset while online unlinks the clock from
    Google, which no restore undoes (the clock then sits on the setup screen, and Cast keeps covering Magisk).

## Before the run

### Factory reset after a restore (not an lck bug, a docs note)
- After restoring run 5's stock backup, the clock was factory reset on the device (both volume buttons, then
  reset on screen) while on Wi-Fi, to clear its saved networks.
- It then showed spinning dots for more than 25 minutes, through a forced restart.
- `lck restore` again brought it back with the backup's device name and Wi-Fi, but on Google's setup screen.
- **Why:** a factory reset while online unlinks the clock from the Google account on Google's side. A restore
  rewrites only the clock, so it can't relink it. The kiosk doesn't need the link.
- **Docs:** to go back to stock, use `lck restore`, never a factory reset. To get the stock clock face back
  after one, set it up again in Google Home.

### Clearing the saved Wi-Fi for the test
- The Wi-Fi test needs a clock with no saved network, so the setup's own backup has none.
- Done on the clock, not in any backup: the stock backup's user data (already unpacked and checksum-checked by
  the restore) was copied, and `<Network>` entries were removed from `/misc/wifi/WifiConfigStore.xml` with
  debugfs, keeping owner 1000:1000, mode 0600 and the `wifi_data_file` label. Networks: 1 before, 0 after.
  `wpa_supplicant.conf` and the per-user store had none. `e2fsck -fn` clean.
- Written back with mtkclient `w userdata` only, over BROM: `Wrote … sector count 10482359`.
- Run 5's stock backup (`lck-e2e5/backup/clock`) was not changed. It's still the way back.

### BROM with VOLUME UP only
- Question from the user: is VOLUME DOWN needed for BROM at all? VOLUME UP alone passes through BROM on the way
  to fastboot (`docs/findings/NOTES.md`), which suggests VOLUME UP is the BROM key and mtkclient waiting is what
  keeps the clock there.
- Every BROM catch today used VOLUME UP only (the userdata write, and all three in the setup backup), confirmed
  by the user. **VOLUME DOWN isn't needed.**
- So BROM's box can say "hold VOLUME UP", like fastboot's, and the guide's "one button alone gives the
  preloader" is wrong for VOLUME UP.

### mtkclient attaching to a stale DA
- A read was stopped partway (Ctrl-C equivalent). The next mtkclient session, started before the clock was
  unplugged, attached to the leftover download agent (`0e8d:2001`), failed every dev ctrl call, and ended with
  "Couldn't detect partition: userdata". Nothing was written, and it exited 0.
- **For lck:** `run_in_brom` should treat `0e8d:2001` at the start as "unplug the clock first", and wait for
  the clock to leave USB before starting mtkclient. Check that `_ok` catches "Couldn't detect partition"
  (it looks for "Error: Couldn't", which matches).
